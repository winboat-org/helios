# DX12.md — the Direct3D 12 charter

**What this is:** an evidence-first survey of where D3D12 actually stands in this tree, the two
strategies that could give Helios a D3D12 surface, what each demands from `kmd_render/` and `umd/`,
a staged bring-up plan with gates, and the landmines this project has already paid for.

**What this is not:** a decision. The tree does not currently contain the evidence needed to choose
between the two strategies, and §2 says exactly what evidence would settle it. It is also not a
schedule — D3D12 is a larger surface than the D3D11 UMD that took this project from Gate 5b to a
composited desktop, and nothing here should be read as implying otherwise.

---

## 1. Where D3D12 stands today — the exact facts

### 1.1 `OpenAdapter12` exists and refuses

`umd/src/adapter.rs:177-189`, verbatim:

```rust
#[no_mangle]
pub unsafe extern "system" fn OpenAdapter12(open_data: *mut c_void) -> Hresult {
    log_error!("OpenAdapter12");
    log_error!("OpenAdapter12 -> DXGI_ERROR_UNSUPPORTED (D3D12 DDI not implemented yet)");
    let _ = open_data;
    DXGI_ERROR_UNSUPPORTED
}
```

The HRESULT is `DXGI_ERROR_UNSUPPORTED` = **`0x887A_0004`**. The choice is deliberate and the
reason is recorded in the comment at `:182-188`: until R801 this site returned
`DXGI_ERROR_DRIVER_INTERNAL_ERROR` (`0x887A_0020`) because the two shared a constant name, so a
D3D12 client's ordinary "this driver has no D3D12 DDI" negotiation was recorded by the runtime and
by ETW as a **driver fault**. The export itself is kept (`:166-168`): "the loader resolves it by
name, and a missing export is a different (worse) failure than a clean refusal."

The INF registers the same DLL for all four entries:
`kmd_render/helios_kmd_render.inx:81` — `HKR,, UserModeDriverName, %REG_MULTI_SZ%,
%13%\helios_umd.dll,%13%\helios_umd.dll,%13%\helios_umd.dll,%13%\helios_umd.dll`. So a D3D12
runtime already loads Helios' UMD and calls `OpenAdapter12`; it is refused at the first statement.

### 1.2 What was deleted, and by which tranche

`umd/src/adapter.rs:104-109`, verbatim:

> The five hand-written `D3d12Ddi*` structs that used to sit here, the eight `d3d12_*` handlers and
> `D3D12_SUPPORTED_DDI_VERSIONS` went with **T6's R908**: the compiler already proved them
> unreachable behind `OpenAdapter12`'s unconditional early return, and `#[allow(unreachable_code)]`
> was silencing that proof. `D3d10_2DdiArgGetCaps` is NOT among them -- the live `get_caps` uses it.

The tranche is **T6, recommendation R908**, landed as commit `e315d03` ("umd: delete the
unreachable D3D12 adapter body behind OpenAdapter12 (R908)"). Its message enumerates what went: the
~40-line adapter-funcs installation block, the eight `d3d12_*` handlers (187 lines),
`D3D12_SUPPORTED_DDI_VERSIONS`, the five `D3d12Ddi*` ABI structs, and — called out as "the worst of
it" — the D3D12 caps policy inside `d3d12_get_caps` (UMA, 3DPIPELINESUPPORT,
`3DPIPELINELEVEL_1_0_CORE`, seven hand-transcribed `D3D12DDICAPS_TYPE_*` values), described as "a
second, divergent copy of the caps-dispatch pattern living in the same file as the live D3D11 one,
reading as a contract a future reader must preserve."

**Read this as a warning, not as a loss.** The deleted code was never reachable; it was a
hand-transcribed ABI surface with no bindgen layout assertions behind it. Any revival starts from
the WDK headers through bindgen, the way `ddi::*` is generated today (R802), not from that deleted
body.

### 1.4 D3D12 references in `kmd_render/`

A case-insensitive grep for `d3d12` across `kmd_render/src/` returns **one** hit:
`kmd_render/src/ddi/create_allocation.rs:1436-1438` — a doc comment noting that
`cross_adapter_pitch` aligns a 32-bpp linear row pitch to `D3D12_TEXTURE_DATA_PITCH_ALIGNMENT`
(256 bytes), the cross-adapter requirement. It is a constant borrowed for a D3D11 cross-adapter
allocation path; the body lives in `helios_kmd_logic`. **It implies nothing about D3D12 support.**

The KMD has no D3D12 awareness of any kind, which is correct — WDDM has no D3D12-specific miniport
DDI. What D3D12 needs from a miniport is a set of *capabilities*, and those are §3.

## 2. The two candidate strategies

### (a) A native D3D12 UMD in `umd/`

Implement the D3D12 UMD DDI (`d3d12umddi.h`) in `umd/`, backed by the same cxx bridge and a
D3D12-capable engine underneath.

**What it requires from the KMD:** materially more than D3D11 does — real multi-engine or an honest
single-engine story, monitored fences the runtime can rely on, residency, and a GPU virtual address
model that is not decorative. See §3 for what exists today.

**What it requires from the UMD:** a second full DDI frontend. D3D12's driver model is not a
superset of D3D11's — command allocators/lists, pipeline state objects, root signatures and
descriptor heaps, resource barriers and explicit state tracking, and a caps surface
(`D3D12DDICAPS_TYPE_*`) that the runtime validates as one contract exactly the way
`CDevice::LLOCompleteLayerConstruction` validates the D3D11 one (`umd/src/caps.rs:30-43`).

**What it reuses:** the adapter plumbing (`OpenAdapter12` export, INF registration, the runtime
adapter handle capture at `adapter.rs:225`), the cxx bridge pattern, the log/knob/counter
infrastructure, the format table (`umd/src/format.rs`), and the whole KMD side.

**What is unknown:** *everything about the engine underneath.* `dxvk-helios/` is DXVK — D3D9/10/11.
It has no D3D12 implementation. A native D3D12 UMD would need either a from-scratch D3D12→Vulkan
translator or vkd3d-proton's `libs/vkd3d` reused as a library behind the DDI, which is strategy (b)
wearing a different hat. **UNVERIFIED:** whether vkd3d-proton's internals are separable from its
`ID3D12Device` COM surface enough to sit behind a UMD DDI. Settling read: inspect
`vkd3d-proton-helios/libs/vkd3d/` for the boundary between the COM layer and the translation core.

### (b) vkd3d-proton in front of the existing Vulkan/Venus path

Ship vkd3d-proton as the D3D12 implementation — apps get `d3d12.dll`/`d3d12core.dll` replaced (the
Proton model) or load vkd3d-proton directly, and it targets the Helios Vulkan ICD.

**What it requires from the KMD:** nothing new for *rendering*. This path does not go through the
D3D12 UMD DDI at all; it goes through Vulkan → venus → the same submit/fence machinery D3D11
already exercises. `OpenAdapter12` stays refusing, honestly.

**What it requires from the UMD:** nothing. `umd/` is not in this path.

**What it reuses:** the entire proven stack — `icd/mesa` venus ICD, the ring/fence chain proven by
`tools/vk_ring_fence_probe.cpp`, the KMD transport, and the LUID identity fix
(`ROADMAP.md:2994-3007`) that already made DXGI-adapter→VkPhysicalDevice matching work for
Vulkan clients such as Steel Nomad.

**What is unknown, and it is the load-bearing unknown:** **presentation.** `ROADMAP.md:2315-2320`
states the problem precisely:

> **CONSEQUENCE:** only the VULKAN client class (native VK games + vkd3d-proton D3D12) lacks a HW
> present — a Vulkan ICD has no runtime handing it the destination surface; that missing hand-off
> IS the entire gap roads (1)/(2)/(4) exist to fill.

A D3D11 UMD gets both `hSurfaceToPresent` and `hDstResource` from `DXGI_DDI_ARG_PRESENT` and does a
GPU-side `CopySubresourceRegion`; a Vulkan ICD gets no such hand-off. The dcomp vehicle
(`tools/dcomp_present_probe.cpp`, ROADMAP 27th/28th sessions) is the current answer for the Vulkan
class, and `ROADMAP.md:2789-2792` records that vkd3d's resize/fullscreen shape — a new `VkSurface`
for the same HWND — is exactly what broke the per-surface target cache before the hwnd→target
registry fix. So the vkd3d path lands squarely on a present path that has already been shown to be
the fragile one.

Also unknown: **what the fork was for** (§1.3), and whether upstream vkd3d-proton runs at all on
this ICD today (**UNVERIFIED** — nothing in the tree records an attempt).

### The decision is open

The tree contains no evidence that selects between (a) and (b). What would settle it, in the order
that costs least:

1. **Does upstream vkd3d-proton run on the Helios ICD at all?** Build the pinned submodule,
   run its own test suite (`icd/mesa/.gitlab-ci/vkd3d-runner.sh` is the upstream harness shape)
   against the guest ICD, and record the pass/fail count. A pass count near a real GPU's makes (b)
   overwhelmingly cheaper; a floor of failures in the Vulkan features vkd3d requires (descriptor
   indexing, buffer device address, timeline semaphores, `VK_KHR_maintenance*`) tells you which
   ICD/host work gates *either* strategy.
2. **What does the venus ICD actually expose?** `vulkaninfo` on the guest against vkd3d-proton's
   documented minimum feature set. This is a read, not a build.
3. **Is a windowed vkd3d-proton D3D12 swapchain presentable today?** Run one D3D12 sample from
   `dx-samples-research-only/Samples/Desktop/` under vkd3d-proton with the dcomp vehicle and check
   the screen (`helios_paintcap` → `Z:\tmp\screen_copy.png` is the only rendering evidence that
   counts). This is the question (b) lives or dies on.
4. **Is vkd3d's translation core separable from its COM layer?** A read of
   `vkd3d-proton-helios/libs/vkd3d/`, needed only if (a) is still live after 1-3.

Until at least 1 and 3 are answered, writing D3D12 DDI code is premature — and R908 is the standing
proof of what unreachable D3D12 scaffolding costs.

## 3. What D3D12 demands from the KMD that D3D11 did not

Ground truth: `kmd_render/src/lib.rs:106-222` sets **84** of the **187** `DxgkDdi*` slots in
`_DRIVER_INITIALIZATION_DATA` (193 fields total in the generated bindings). The 103 unset slots are
the interesting part.

### 3.1 Command queues, command lists and multi-engine — **partial, single-node**

| Fact | Where |
|---|---|
| Exactly one engine node, `DXGK_ENGINE_TYPE_3D` | `kmd_render/src/ddi/query_adapter_info.rs:1254-1278` |
| `NbAsymetricProcessingNodes = 1` | `query_adapter_info.rs:456-464` |
| `SchedulingCaps = MultiEngineAware \| PreemptionAware` | `query_adapter_info.rs:304-305, 395` |
| `DxgkDdiQueryDependentEngineGroup` / `QueryEngineStatus` / `ResetEngine` accept `NodeOrdinal==0 && EngineOrdinal==0` only, `STATUS_INVALID_PARAMETER` otherwise | `kmd_render/src/ddi/scheduler.rs:55-123` |
| `DxgkDdiCreateContext` ignores `NodeOrdinal`, `EngineAffinity` and `Flags` entirely; sets `DmaBufferSegmentSet=1`, `DmaBufferSize=256 KiB`, `AllocationListSize = PatchLocationListSize = DXGK_ALLOCATION_LIST_SIZE_GDICONTEXT` | `kmd_render/src/device.rs:389-431` |
| `MaxAllocationListSlotId = 0xFFFF` | `query_adapter_info.rs:217` |

**Hardware scheduling is refused, deliberately and consistently.** `DxgkDdiCreateHwQueue` returns
`STATUS_NOT_SUPPORTED` and records `HwQRef` (`scheduler.rs:180-187`);
`DxgkDdiSubmitCommandToHwQueue` returns `STATUS_NOT_SUPPORTED` (`:198-208`);
`DxgkDdiPresentToHwQueue` returns `STATUS_NOT_SUPPORTED` and records `PHQcall`/`PHQours`/`PHQst`
(`:238-252`). The doc comment at `:199-209` explains why the refusal is at *queue creation*: the
old shape handed back a queue handle and then failed the submission, "the worst possible pairing,
because the scheduler has already committed to the queue by the time the submission fails" — the
VidSch `0x119`/Arg1=2 bugcheck shape. Evidence recorded there: `PHQcall` is **absent** from the
service key, i.e. `PresentToHwQueue` has never been called in the key's lifetime.

*What this means for D3D12:* a D3D12 device on this adapter would get one 3D queue. `COPY` and
`COMPUTE` command queues, and anything relying on hardware-queue submission (GPU upload heaps,
user-mode submission), are not backed. Whether dxgkrnl's software scheduler will synthesise the
COPY/COMPUTE queues over one node, or whether D3D12 device creation requires more nodes, is
**UNVERIFIED** — settling read: the WDDM node/engine requirements for D3D12 in the WDK docs, then
an actual `D3D12CreateDevice` attempt once `OpenAdapter12` returns something other than a refusal.

### 3.2 Residency (`OfferAllocations` / `ReclaimAllocations`) — **not a miniport surface here**

**Verified:** the string `Offer` does not appear as any DDI name in the generated
`_DRIVER_INITIALIZATION_DATA` (8 `Offer` hits in the whole 100 741-line bindings file, all of them
the `OfferPriority` bitfield of an argument struct). There is no `DxgkDdiOfferAllocations` or
`DxgkDdiReclaimAllocations` slot to implement in this WDK, so "the KMD does not implement them" is
not a meaningful gap statement.

What the KMD *does* implement on the residency path: `DxgkDdiBuildPagingBuffer`
(`kmd_render/src/ddi/build_paging_buffer.rs`), `DxgkDdiCreateAllocation`/`DestroyAllocation`,
`OpenAllocation`/`CloseAllocation`, `DescribeAllocation`, `MapCpuHostAperture`/`UnmapCpuHostAperture`
— all set (`lib.rs:151-156, 211-215`).

`DXGK_VIDMMCAPS.DriverManagesResidency` exists in the bindings (`tmp/dxgk_bindings.rs:43357`) and is
**not set** by this driver — `MemoryManagementCaps` is assembled at `query_adapter_info.rs:334-341`
from `SectionBackedPrimary` plus optionally `CrossAdapterResource` (knob), `VirtualAddressingSupported`
and `GpuMmuSupported`. Residency is therefore dxgkrnl/VidMm's job, which is the right default.

**UNVERIFIED:** whether D3D12's residency model (`MakeResident`/`Evict`, residency budgets from
`QueryVideoMemoryInfo`) behaves sanely against this adapter's segment topology — one aperture
segment (id 1) plus one CPU-host-aperture BAR memory segment (id 2), with the aperture reported
FIRST and the CPU-host-aperture segment reported LAST (`kmd_render/src/ddi/gpummu.rs:68-95`, and the
CLAUDE.md invariant). Settling read: `tools/vram_report_probe.cpp` already compares DXGI/VidMm
numbers against Venus heaps; extend it once a D3D12 device can be created.

### 3.3 Tiled / reserved resources — **claimed at D3D11, unmodelled at the KMD**

The UMD advertises `D3D11_OPTIONS1` tiled-resources **Tier 2** for every FL11 device
(`umd/src/caps.rs:64, 81`) and installs the seven tiled DDIs in the WDDM1_3 device-funcs table
(`umd/src/forward/tables.rs:296-303`), forwarding to DXVK's `ID3D11DeviceContext2` methods
(`umd/src/forward/tiles.rs`).

The KMD models nothing of it. There is no tile-pool concept, and the page tables are explicitly
**decorative** — `kmd_render/src/ddi/gpummu.rs:1-14`:

> Helios has no guest GPU MMU: venus addresses host resources by opaque id and the **host GPU owns
> the real MMU**, so the guest page tables are *decorative* — their content is never read by any
> hardware. What is NOT optional is the *structural* bookkeeping VidMm maintains regardless.

D3D12 reserved resources are defined in terms of real GPU VA remapping. On this stack the mapping
that matters happens host-side inside venus. **Status: the D3D11 claim is DXVK's to honour; the
D3D12 equivalent is unmodelled and its feasibility is UNVERIFIED.** Settling read: whether
vkd3d-proton's sparse-resource implementation works over venus at all (question 1 in §2).

### 3.4 GPU virtual address management — **declared, and decorative**

Verified declarations:

- `WddmSurface::Wddm2_1GpuMmu` is the live level (`kmd_render/src/ddi/wddm_surface.rs:64`). One
  constant drives five coupled sites: `DRIVER_INITIALIZATION_DATA.Version` →
  `DXGKDDI_INTERFACE_VERSION_WDDM2_1`, `DRIVERCAPS.WDDMVersion` and `WDDMDEVICECAPS.WDDMVersion` →
  `DXGKDDI_WDDMv2_1`, the `VirtualAddressingSupported|GpuMmuSupported` bits, and
  `GetNodeMetadata.GpuMmuSupported` (`wddm_surface.rs:66-102`).
- ⚠ **The adapter reports WDDM 2.1, not 3.2.** `wddm_surface.rs:30-33` is explicit: "CLAUDE.md's
  'WDDM 3.2 miniport' describes the DDI table's ABI shape (the bindgen structs are the 26100/3.2
  ones), not the level this reports." 3.2 is a *named but unselected* level because DWM treats a
  WDDM 2.2+ display adapter as a Display-Core/MPO3 device, Helios registers no MPO3 interface, and
  DWM then fails fast at `E_NOTIMPL` (`:25-28`). D3D12 requires WDDM 2.0+, so 2.1 is not itself a
  blocker.
- The geometry (`gpummu.rs:44-65`): 40-bit GPU VA, 4 KiB pages, 4 levels (9+9+9+1), every table one
  4 KiB page in **system memory segment 0**, `PageTableUpdateMode = GPU_PHYSICAL`, and every
  optional `DXGK_GPUMMUCAPS` bit left at 0 ("unknown stays unadvertised", `:122-126`).
  `CPU_VIRTUAL` was proven wrong by KD — it dies inside `VIDMM_PAGE_TABLE_BASE::GetCpuVisibleAddress`
  (`:27-35`).
- The page-table update DDIs `DxgkDdiUpdatePageTable`, `UpdatePageDirectory`, `MovePageDirectory`
  and `DescribePageTable` are **unset** — consistent with `GPU_PHYSICAL` mode, where PTE writes
  arrive through `BuildPagingBuffer(UPDATE_PAGE_TABLE)` + `SubmitCommand`, which the null engine
  consumes and no-ops. `DxgkDdiSetRootPageTable` and `GetRootPageTableSize` **are** set
  (`lib.rs:217-218`).

*What this means for D3D12:* D3D12 exposes GPU virtual addresses to applications
(`ID3D12Resource::GetGPUVirtualAddress`, root-signature root descriptors, indirect argument
buffers, ray-tracing acceleration-structure addresses). On this stack there is no guest VA that
means anything — the addresses VidMm assigns are bookkeeping and the real addressing is host-side
by opaque venus id. **A D3D12 UMD would have to invent an app-visible VA space and map it to venus
ids itself.** For strategy (b) this is a non-issue: vkd3d-proton uses Vulkan buffer device address,
which the host GPU resolves natively. That asymmetry is currently the strongest *technical* argument
in the tree for (b) — and it is an argument about difficulty, not about whether (b) works.

### 3.5 Other unset slots worth knowing about before planning

From the 103 unset (`lib.rs` vs the generated struct):

- **Fences:** `DxgkDdiSignalMonitoredFence`, `DxgkDdiCreateNativeFence`, `DestroyNativeFence`,
  `OpenNativeFence`, `CloseNativeFence`, `SetNativeFenceLogBuffer`, `UpdateNativeFenceLogs`.
  Monitored fences nonetheless *work* on the software-scheduled path — `tools/vehicle_flipwait_probe.c`
  proves VidSch honours a queued `WAIT(F>=1)` before a `SIGNAL(G=5)`. D3D12's `ID3D12Fence` maps to
  monitored fences, so this is a "verify, don't assume" area, not a known blocker.
- **User-mode submission:** `DxgkDdiCreateDoorbell`, `ConnectDoorbell`, `DisconnectDoorbell`,
  `DestroyDoorbell`, `NotifyWorkSubmission` — all unset. Not required for a baseline D3D12 device.
- **Context scheduling:** `SetContextSchedulingProperties`, `SuspendContext`, `ResumeContext`,
  `SetupPriorityBands`, `NotifyContextPriorityChange`, `SetSchedulingLogBuffer` — unset. D3D12
  command-queue priorities have nowhere to land.
- **Protected content:** `CreateProtectedSession`, `DestroyProtectedSession`,
  `SetVideoProtectedRegion` — unset.
- **MPO:** the whole `CheckMultiPlaneOverlaySupport*` / `SetVidPnSourceAddressWithMultiPlaneOverlay*`
  / `GetMultiPlaneOverlayCaps` / `PostMultiPlaneOverlayPresent` family — unset (and §3.4 records why
  the adapter deliberately stays below the MPO3 boundary).

## 4. A staged bring-up plan

Each stage: an entry condition, a measurable exit gate, and a named artifact. Stages D0-D2 are
reads and experiments; **no D3D12 DDI code is written before D3 selects a strategy**, because R908
is the record of what happens otherwise.

### D0 — Baseline: does the Vulkan substrate carry D3D12 at all?
*Entry:* none; this is a read plus one build.
*Work:* build the pinned `vkd3d-proton-helios` submodule for Windows; capture `vulkaninfo` on the
guest and diff it against vkd3d-proton's documented required feature set; run vkd3d-proton's own
test suite against the guest ICD.
*Exit gate:* a recorded pass/fail count from the test suite and a named list of missing Vulkan
features/extensions, each attributed to venus, to the host virglrenderer, or to the Mesa ICD fork.
*Artifact:* `tmp/dx12/D0-substrate.md` + the raw suite log. Also: the answer to "what was the fork
for" if the build turns up local divergence (§1.3 says there is none today).

### D1 — One D3D12 frame on the screen, by any means
*Entry:* D0 shows the substrate is not missing something structural.
*Work:* run one sample from `dx-samples-research-only/Samples/Desktop/` under vkd3d-proton, in
session 1 via a cloned scheduled task (`tmp/perf/launch-gt1-arm.ps1` is the five-line recipe).
*Exit gate:* **owner-visible desktop evidence** — `helios_paintcap` → `Z:\tmp\screen_copy.png`
showing the sample's output, plus a clean `tools/umd-gate-surface.ps1 -AllProcesses` and a
`tools/kmd-counter-snapshot.ps1` diff with all failure counters at 0. Log lines are not frames.
*Artifact:* the screenshot, the two gate captures, and `tmp/dx12/D1-first-frame.md`.

### D2 — Characterise the vkd3d present path
*Entry:* D1 produced a frame.
*Work:* measure the present path for a D3D12 client the way WS2 measured D3D11 — the VNC RFB
sampler (`tools/vnc_frame_probe.py` + `tools/vnc_scanout_correlate.py`) with a completeness-oracle
rectangle, correlated against the QEMU `virtio_gpu_cmd_res_flush` trace on the same clock. Exercise
the shapes ROADMAP already flagged: resize, fullscreen transition, and a second `VkSurface` on the
same HWND (`tools/vk_surface_recreate_probe.cpp`).
*Exit gate:* a black-frame percentage and a present-to-scanout distribution for a D3D12 client,
comparable to the D3D11 numbers in `ROADMAP.md` (0ab-A/B/C), and either zero occurrences of the
one-target-per-HWND failure or a filed defect with a reproducer.
*Artifact:* `tmp/dx12/D2-present.md` with the numbers, plus any new ROADMAP defect entries.

### D3 — The strategy decision
*Entry:* D0-D2 complete.
*Work:* write the decision against the four settling questions in §2, with the measurements from
D0-D2 attached. If (b): decide packaging (how `d3d12.dll`/`d3d12core.dll` reach an app) and whether
`OpenAdapter12` stays refusing forever — it should, and the refusal comment should then cite this
document. If (a): scope the DDI surface from the WDK headers **through bindgen**, with layout
assertions, and budget it honestly against the D3D11 UMD's size (`ROADMAP.md:3155-3156`:
"`forward.rs` implements ~220 DDI functions").
*Exit gate:* a decision recorded in this file with its evidence, and `ROADMAP.md` updated with the
chosen workstream.
*Artifact:* §2 of this document, rewritten from "open" to a decision.

### D4+ — Execution (shape only, deliberately unscoped)
*If (b):* packaging, an install/verify path (`packaging/windows/Verify-Helios.ps1` gains a D3D12
smoke probe), a soak against the D3D12 samples, and a conformance baseline from vkd3d-proton's own
suite.
*If (a):* bindgen'd `d3d12umddi` bindings with layout assertions → `OpenAdapter12` caps negotiation
→ device/queue/list creation → PSO and root signatures → descriptor heaps → barriers → present.
Every stage gated the way D3D11's were: a named counter for every refusal, a probe that proves the
stage, and owner-visible evidence for anything that claims to draw.

## 5. Risks and known landmines

1. **Never build a second unreachable DDI surface.** R908 (`umd/src/adapter.rs:104-109`, commit
   `e315d03`) exists because a ~230-line D3D12 body sat behind an unconditional early return,
   maintained and reviewable, with `#[allow(unreachable_code)]` silencing the compiler's proof that
   it was dead. If D3D12 code is written, `OpenAdapter12` must stop refusing in the same commit that
   makes it reachable — or the code must not be written yet.

2. **Never stub silently** (CLAUDE.md rule 2). Every skipped or refused path gets a named counter.
   The KMD's hardware-queue refusal is the model: `CreateHwQueue` refuses at the *first* step and
   records `HwQRef`, so a submission against a queue that does not exist is unrepresentable
   (`kmd_render/src/ddi/scheduler.rs:167-187`). The shape it replaced — succeed at create, fail at
   submit — is the VidSch `0x119`/Arg1=2 bugcheck.

3. **A panic in any DDI is a silent graphics deadlock** (CLAUDE.md key invariants). No `panic!`,
   `todo!` or `unwrap` on runtime-supplied data in a release path; return a documented error from
   that DDI's legal return set. An illegal NTSTATUS is itself logged by dxgkrnl as a driver bug.

4. **Hand-transcribed ABI structs are how R908's body went wrong.** Every DDI struct comes from the
   WDK header through bindgen with size/alignment/offset assertions (R802). `adapter.rs:36-45`
   records what hand transcription cost once already: a 376..392-byte out-of-bounds write into the
   runtime's heap from an `else`-as-default in the interface dispatch.

5. **Advertising a capability that is not backed is a lie the OS acts on.** `SupportDirectFlip=1`
   was an unbacked bring-up advertisement that made DWM stop compositing an eligible visual while
   every fence stayed green (`query_adapter_info.rs:439-455`); `FlipImmediateMmIo` opted into a
   contract requiring the flip to be complete when `SetVidPnSourceAddress` returns, which arrives at
   DIRQL where a virtio round-trip is illegal — 80 dropped binds and 145 of 1245 present markers
   writing the buffer already on screen (`:377-388`). D3D12's tiered caps invite this exact mistake.

6. **The GpuMmu declaration is load-bearing and fragile.** `wddm_surface.rs:93-96`: declaring GPU VA
   re-engages the VidMm paging path that historically bugchecked (`InitDmaPools` Code-43,
   `0x10E:0x49`). The five coupled sites must move together — that is why they are one constant.

7. **The boot-path kernel stack has 368 bytes of headroom.** `DxgkDdiStartDevice` +
   `VirtioGpu::init` measured 17 568 B against a 17 936 B known-good ceiling (`ROADMAP.md:3327-3335`).
   Overflow at boot gives `0xc0000001`/Startup Repair with **no dump and no bugcheck event**, and
   does not reproduce on a live `devcon` restart. Run `tools/kmd-frame-sizes.ps1` on every image.

8. **Session 0 fakes driver regressions** (memory: 60th session) — anything with a window goes
   through a cloned scheduled task. **Registry counters persist across boots** — verify a counter
   *moves* this boot; `tools/kmd-counter-snapshot.ps1` exists to diff two snapshots.

9. **Never blame the host stack without host-side evidence.** The host is proven good, and
   virglrenderer's `vkr_log`/`proxy_log` are INFO-level and therefore **silent** on the release
   build — absence of host log lines below WARNING proves nothing. A real host-side bisect needs a
   relaunch with `VIRGL_LOG_LEVEL=debug` (`ROADMAP.md:3431-3434`), and VM relaunches are
   owner-gated.
