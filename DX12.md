## 1. The decision

**Helios ships a real D3D12 user-mode display driver: `helios_umd12.dll`, implementing
`d3d12umddi.h`, forwarding into vkd3d-proton's `ID3D12*` COM objects.**

It is the D3D11 architecture with two boxes swapped, and nothing else changed:

```
              D3D11 (shipping today)                    D3D12 (target)
  MS d3d11.dll + dxgi.dll                     MS d3d12.dll + D3D12Core.dll + dxgi.dll
    │  d3d10umddi DDI                           │  d3d12umddi DDI
    ▼  UserModeDriverName[2]                    ▼  UserModeDriverName[3]        ← the only new slot
  helios_umd.dll (Rust)                       helios_umd12.dll (Rust)          ← the only new DLL
    │  cxx bridge                               │  cxx bridge
    ▼                                           ▼
  DXVK engine (ID3D11Device)                  vkd3d-proton engine (ID3D12Device)
    └───────────────────┬───────────────────────┘
                        ▼
       Mesa venus ICD → D3DKMTEscape → kmd_render → virtio-gpu → virglrenderer → host GPU
                        (unchanged, and already compositing the desktop)
```

Everything below the bridge already ships and is already proven. That is the whole argument for this
shape: it reuses the half of the stack that took this project two years to build, and confines the
new work to one DLL that nothing else loads.

**Why a driver rather than just shipping vkd3d's DLLs next to applications.** There is no supported
system-wide `d3d12.dll` replacement on Windows 11 — `System32\d3d12.dll` is WRP/TrustedInstaller
protected, and the Agility SDK's `D3D12SDKVersion`/`D3D12SDKPath` mechanism is keyed off the
*application's own exports* and swaps only `D3D12Core.dll`, never the driver. App-local DLL
placement reaches only applications whose directory you control: never dwm, never Store apps, never
an unmodified installer. A driver is the only shape that makes *the adapter* D3D12-capable
(`docs/dx12/research/R10-prior-art.md` Q6, `R11-registration-packaging.md` §5.2).

⛔ **There is no app-facing vkd3d arm** (owner directive, `DECISIONS.md` D2). Helios never ships,
deploys or measures vkd3d's `d3d12.dll`/`d3d12core.dll` as an application's D3D12. Everything
app-facing goes through Microsoft's `d3d12.dll` + `D3D12Core.dll` + `dxgi.dll` and lands on
`helios_umd12.dll`, exactly as D3D11 does today — which also means **DXVK's `dxgi.dll` is not
needed anywhere**, and never was for the shipping path (`umd/build.rs:238-243`: a WDDM UMD sits
below DXGI and *implements* the DXGI DDI).

The question that arm would have answered — *does vkd3d actually run on venus, before ~200 DDI
slots are written on the assumption that it does?* — is answered instead by two **headless** steps
that need no DXGI, no swapchain and no app-facing D3D12: the **bridge probe** (`D12-G1`) and the
**headless conformance baseline** (`D12-G2`; the vkd3d suite creates zero swapchains — verified).
See `DECISIONS.md` D2 for what that trade costs.

## 2. What the research settled, in five lines

1. **The substrate is not the problem.** Measured live against vkd3d-proton's own Vulkan profile,
   the Helios guest satisfies **`VP_D3D12_FL_12_2_baseline` in full** — zero feature misses, zero
   extension misses, all nine of vkd3d's hard device-creation gates passed, sparse binding end to
   end, DXR tier 1.1 reachable. (`docs/dx12/SUBSTRATE.md`; capture in `docs/dx12/research/`.)
2. **The KMD is not the problem either.** The work list is three small items, none required for
   the first triangle. Of the 103 unset `DxgkDdi*` slots, 72 are
   unreachable at the declared WDDM 2.1 level and **none of the reachable 31 is required for a
   baseline D3D12 device**. (`docs/dx12/KMD_IMPACT.md`.)
3. **The DDI is ~1.2× the D3D11 UMD in slot count** — **214** slots across four tables, ~86-99 of
   them needing real bodies for a triangle on screen — but **it is undocumented**. Microsoft publishes
   ~600 auto-generated stubs with no Remarks and zero conceptual articles, and there has never been
   a public D3D12 UMD, open or closed. (`docs/dx12/DDI_REFERENCE.md`.)
4. **Presentation reuses the D3D11 machinery.** A D3D12 frame goes MS DXGI → the runtime →
   `pfnPresent` (on the command-list table, plus `D3D12DDI_TABLE_TYPE_DXGI`) → `DxgkDdiPresent` →
   the existing flip arm → `set_scanout_blob`. `pKTCallbacks` carries `pfnRenderCb`/`pfnPresentCb`,
   so even the per-present identity channel transfers unchanged. The ICD's dcomp vehicle and its
   costs are **not** on this path. (`docs/dx12/PRESENT.md`.)
5. **The fence question that looked strategy-deciding is largely answered.** Monitored fences advance
   on this adapter with no GPU-side write, by the documented software path
   (`SignalSynchronizationObjectFromGpuCb` → dxgkrnl updates the fence memory), and
   `tools/vehicle_flipwait_probe.c` already proves the primitive live here with zero KMD changes.
   Risk downgraded HIGH → MEDIUM with a named probe to close it. (`docs/dx12/DECISIONS.md` §6.)

## 3. Where D3D12 stands in the tree today

### 3.1 `OpenAdapter12` exists and refuses

`umd/src/adapter.rs:177-189` returns `DXGI_ERROR_UNSUPPORTED` (`0x887A_0004`). The choice is
deliberate: until R801 it returned `DXGI_ERROR_DRIVER_INTERNAL_ERROR` (`0x887A_0020`) because the
two shared a constant name, so a D3D12 client's ordinary "this driver has no D3D12 DDI" negotiation
was recorded by the runtime and by ETW as a **driver fault**. The export itself is kept because a
missing export is a worse failure than a clean refusal.

⚠ **`dwm.exe` already calls it in production.** Enabling D3D12 is a change to the compositor's
behaviour on the next boot, which is why D3D12 ships behind an off-by-default kill switch
(`docs/dx12/DECISIONS.md` D11).

### 3.2 What was deleted, and why it is a rule and not a loss

`umd/src/adapter.rs:104-109` records T6's **R908** (commit `e315d03`): five hand-written `D3d12Ddi*`
ABI structs, eight `d3d12_*` handlers, `D3D12_SUPPORTED_DDI_VERSIONS` and a whole hand-transcribed
caps policy sat behind `OpenAdapter12`'s unconditional early return, with
`#[allow(unreachable_code)]` silencing the compiler's proof that it was dead.

⛔ **The standing rule:** `OpenAdapter12` must stop refusing **in the same commit** that makes its
body reachable — or the body must not be written yet. And every DDI ABI struct comes from the WDK
header through bindgen with `layout_tests(true)`, never by hand.

### 3.3 The `vkd3d-proton-helios` submodule

Upstream `HansKristian-Work/vkd3d-proton` at `2c7ba22c`, **zero local commits, clean tree** — the
"fork" has never diverged, and no document explains what it was forked for. Two facts a builder
needs before anything else:

- ⚠ Its own three nested submodules (`subprojects/dxil-spirv`, `khronos/Vulkan-Headers`,
  `khronos/SPIRV-Headers`) are **uninitialised empty directories**. Nothing configures, let alone
  builds, until `git submodule update --init --recursive` runs inside it.
- ⚠ The checkout's `origin` is upstream, not the `.gitmodules` fork URL. Any Helios change needs the
  fork wired as a push remote first.

The fork's likely **first real content** is already identified: extending vkd3d's shader-model
denorm exemption to cover the layered venus case, if the probe in §5 says it is needed.

## 4. The plan

Eight phases. Each has an entry condition and a gate from `docs/dx12/GATES.md`. P0 and P1 write no
driver code — **no D3D12 DDI code exists before P2**, because R908 is the standing record of what
unreachable D3D12 scaffolding costs. ⛔ Nothing in this plan deploys vkd3d as an application's
`d3d12.dll` (D2); P0 is **headless engine validation**, not an app-facing arm.

| Phase | What | Gates | KMD | UMD | Ends when |
|---|---|---|---|---|---|
| **P0** Engine validation (headless) | Init vkd3d's nested submodules; build vkd3d (Linux mingw cross); a `tools/` bridge probe that `LoadLibrary`s `helios_vkd3d.dll`, calls `helios_vkd3d_create_device`, renders offscreen and reads back; then the headless conformance baseline | G0–G2 | none | none (a `tools/` probe) | vkd3d demonstrably produces correct pixels on venus, with a recorded conformance triple. **No DXGI, no swapchain, nothing on screen** |
| **P1** Contract capture | The WARP spy proxy: forward `OpenAdapter12` to `d3d10warp.dll` and log the real call sequence, caps queries, table fills and version negotiation | G5 | none | none (a `tools/` probe) | The undocumented contract questions in `DDI_REFERENCE.md` §15 are answered from a log |
| **P2** The split | `umd_common` extraction (stages S1–S2), then the `umd12` crate with bindgen'd `d3d12umddi` and layout assertions. `OpenAdapter12` **still refuses** | G6 | none | scaffolding | D3D11 is byte-for-byte unchanged in behaviour and Fire Strike is at parity |
| **P3** Device | Adapter funcs, the caps answer, `CreateDevice`, the vkd3d bridge. `OpenAdapter12` stops refusing **in the commit that makes it reachable** | G7 | K1 counter half | ~30 slots real | `D3D12CreateDevice` succeeds through `helios_umd12.dll` |
| **P4** First frame | The real-body functions (`DDI_REFERENCE.md` §14 owns the list): descriptor heaps, root signatures, PSOs, resources, command recording, `ExecuteCommandLists`, fences, present | G8 | none | the §14 set | **The first D3D12 pixels on the Helios desktop, owner-visible** — and this is also the first exercise of the D3D12 present path |
| **P5** Conformance | The same vkd3d suite binary, now against the **system** `d3d12.dll`; drive the delta against the P0 baseline to zero | G9 | K1 re-read | the long tail | DDI-arm conformance is at parity with the P0 baseline |
| **P6** Real workloads | 3DMark Night Raid, then Time Spy Graphics | G10 | K2 (paired A/B), K3 | fixes | Night Raid scores; Time Spy Graphics has a 3-run median |
| **P7** Stability & ship | TDR, device restart, resize, buffer rotation, DWM recovery, cold boot; INF, signing, `Verify-Helios`, CI | G11 | — | packaging | The stability list passes and the bundle builds D3D12 in CI |

⚠ **The consequence of D2 that shapes the schedule: the first pixel on screen moves from P0 to P4.**
Under the old plan an app-local vkd3d demo would have drawn a triangle before any Helios code
existed. Now nothing is visible until the DDI can present. That is the deliberate trade — one
present path instead of two — and it is why P0's headless gates matter more, not less: they are the
only thing standing between a wrong assumption about the engine and ~200 DDI slots written on top
of it.

**Parallel track, any time after P0:** the substrate work items — `VK_KHR_external_memory_win32`
(**V1**: absent, and vkd3d uses it *unguarded*, so shared heaps are hazardous rather than degraded)
and the missing 32-bit venus ICD (**V2**). Neither blocks P0–P4.

## 5. Run this first

**One read-only Vulkan probe, no build, no driver change, no reboot** — it decides whether Helios'
D3D12 ceiling is Shader Model 6.0 / FL 12_1 or SM 6.6+ / FL 12_2, and it is a ~40-line program.

vkd3d gates SM 6.2 (and therefore everything above it) on FP32 denorm control, exempting only
`VK_DRIVER_ID_NVIDIA_PROPRIETARY`. The guest reports `MESA_VENUS` with both denorm properties
`false`. **But** vkd3d handles layered implementations: with `VK_KHR_maintenance7` it reads the
*underlying* driver's properties and swizzles `driverID` to the real one
(`vkd3d-proton-helios/libs/vkd3d/device.c:2657-2664`), and that runs at `device.c:4129`, well before
shader-model caps init at `:11599`. The guest has `maintenance7` and reports `layeredApiCount = 1`
naming the host NVIDIA device — but nothing has ever chained the nested
`VkPhysicalDeviceDriverProperties` to confirm the real `driverID` comes through.

Write `tools/vk_layered_driverid_probe.cpp`: chain
`VkPhysicalDeviceLayeredApiPropertiesListKHR` → `VkPhysicalDeviceLayeredApiVulkanPropertiesKHR` →
`VkPhysicalDeviceDriverProperties` and print `driverID`.

- Prints `VK_DRIVER_ID_NVIDIA_PROPRIETARY` ⇒ SM 6.6 and FL 12_2 are on the table (`SUBSTRATE.md`
  §7.1 walks vkd3d's ladder to 6.7 from there).
- Prints `0` or `MESA_VENUS` ⇒ the ceiling is SM 6.0 / FL 12_1, and the vkd3d fork gets its first
  justified patch — which must be conditioned on something venus can actually observe about the
  host, never hardcoded.

Details and the three candidate fixes: `docs/dx12/SUBSTRATE.md` §7.

## 6. Risks and landmines

The generic ones are in `docs/dx12/DECISIONS.md` §7 and are not repeated here. The D3D12-specific
ones, ranked:

1. **⚠ Nothing is visible until P4, so P0's headless gates are the only early truth.** `D12-G1`
   (the bridge probe reads back correct pixels from `helios_vkd3d_create_device`) and `D12-G2` (the
   headless conformance triple) are what stop ~200 DDI slots being written on top of an engine that
   does not work on venus. Do not skip them because nothing is on screen yet.
   *(The old risk here — an app-local DXVK `dxgi.dll` silently demoting Phase-0 frames to the
   software GDI blit — is closed by D2, which removes app-local DLLs entirely. The failure shape
   is still worth remembering: a correct-looking picture served by a path you did not intend, which
   is why `D12-G8` must confirm which path served the frame, not merely that a frame appeared.)*
2. **⚠ D3D12's 43 caps types and 14 tiered enums are the densest version of the
   advertise-only-what-is-backed hazard this project has faced.** `SupportDirectFlip=1` made DWM
   stop compositing while every fence stayed green; `FlipImmediateMmIo` opted into a contract that
   required a virtio round-trip at DIRQL. The D3D12 runtime cross-checks tiers against each other
   and against shader models, and says so in its own validation strings
   (`docs/dx12/research/d3d12core-driverstrings.txt`). ⛔ `VKD3D_FEATURE_LEVEL` and the test
   binary's `--feature-level` must never appear in a gate run — they raise advertised tiers without
   backing them.
3. **⚠ Honour `pfnFillDDITable`'s `SIZE_T` argument.** D3D12 hands the driver a runtime-supplied
   table buffer *with its size*. Writing `size_of::<T>()` bytes is the R702 class (24H2 passed
   576 bytes for a 592-byte `DRIVERCAPS`), and here it is parameterised explicitly, so there is no
   excuse.
4. **⚠ The struct-return ABI on descriptor handles.** `pfnGetCPU/GPUDescriptorHandleForHeapStart`
   return the handle **by value**; vkd3d's C implementation returns via hidden pointer. Same defect
   class as the `bridge_guard` truncation (`ead692e`) that crash-looped dwm and LogonUI at cold
   boot. Handle it explicitly in the bridge; do not assume.
5. **⚠ Two engines in one process.** A D3D12 title with a D3D11 overlay, or any app on a desktop dwm
   composites, means DXVK and vkd3d live together: two Vulkan instances against one venus ICD, two
   ICD module resolutions, two logging globals. The ICD's process-global state was already audited
   once for the two-live-`VkInstance` shape; re-read that audit before assuming.
6. **⚠ Two SPIR-V compilers must not land in one DLL by accident.** DXVK links `libdxbc_spv.a` +
   `libspirv.a`; vkd3d links `dxil-spirv` + `libvkd3d-shader.a`. Both are C++ SPIR-V producers built
   over SPIRV-Headers, and whether their *defined external* symbol sets intersect is **UNVERIFIED**.
   `DECISIONS.md` D4's DLL boundary makes the question moot; a static-link variant must settle it
   first. *(Licence is explicitly not a factor — owner directive, `DECISIONS.md` D4 reason 2.)*
7. **⚠ D3D12 cross-process / cross-API resource sharing is likely broken on native Windows** under
   vkd3d, because its shared-handle path depends on a Wine-private escape and a Wine device node.
   It does not block a first milestone; do not plan a feature on it.
8. **⚠ The boot-path kernel stack has 368 bytes of headroom** and **session 0 fakes driver
   regressions** and **registry counters persist across boots** — all unchanged, all still true.
   Run `tools/kmd-frame-sizes.ps1` on every KMD image; run anything with a window through a cloned
   scheduled task; verify a counter *moves this boot*.
