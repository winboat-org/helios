# SPECS.md — `microsoft.github.io/DirectX-Specs`, triaged against what Helios actually needs

**What this is.** A triage of every document in Microsoft's published DirectX functional-specification
corpus, scored by how much DDI content it carries *that exists on this Windows build*, and pointed at
the section of the Helios doc set that owns it. It exists so the next session does not have to re-read
90 documents to find the four that matter.

**The pin.** `github.com/microsoft/DirectX-Specs` @ **`2bd58ca5b3d6c56b1a295450d2a8d6bc11d513d7`**,
dated **2026-07-28**, cloned to `tmp/dx12/specs` (gitignored). These are living documents that ship
with Agility SDK releases — **a citation into them without this SHA is the citation-drift class that
cost `DDI_REFERENCE.md` §17.2 ten fixes.** Re-clone with:

```bash
git clone --depth 1 https://github.com/microsoft/DirectX-Specs tmp/dx12/specs
git -C tmp/dx12/specs log -1 --format='%H %cd' --date=short   # must print the SHA above
```

⚠ **The rendered index is not the corpus.** `D3D12AsyncCommands.md` (84 KB, 260 DDI symbol
occurrences) is in the repo and is **not** linked from `https://microsoft.github.io/DirectX-Specs/`.
Enumerate `tmp/dx12/specs/d3d/*.md`, never the index page.

## 1. The premise this corpus corrects, and the part it does not

`DDI_REFERENCE.md`, `DECISIONS.md` H1, `DX12.md` and `GATES.md` all said some version of *"Microsoft
ships ~600 auto-generated reference stubs with no Remarks and zero conceptual articles."*

**That is true of the driver-docs corpus** (`learn.microsoft.com/windows-hardware/drivers/ddi/`) and it
stays true — the three `d3d12umddi` pages this corpus links to
(`ne-d3d12umddi-d3d12ddicaps_type`, `nc-d3d12umddi-pfnd3d12ddi_createfence`,
`nc-d3d12umddi-pfnd3d12ddi_checkresourceallocationinfo_0088`) are exactly such reference stubs, so
they confirm the claim rather than refute it.

**It is not true of DirectX-Specs**, which the repo had touched for two pages before this session
(`D3D12RuntimeBypass`, `D3D12Redistributable`) plus the archived D3D11.3 spec. Measured at the pin:

| | |
|---|---:|
| spec documents under `d3d/` | **90** |
| …containing `D3D12DDI_*` / `PFND3D12DDI` / `D3D12DDIARG` | **47** |
| …with an explicit `DDI` **section heading** | **44** |
| `PFND3D12DDI_*` typedefs in SDK 10.0.26100.0 | **399** |
| …of those, **named in corpus prose** | **123 (31 %)** |
| distinct `PFND3D12DDI_*` named in the corpus | **296** |
| …**absent** from SDK 26100 (newer Agility SDK surface) | **173 (58 % of what the corpus names)** |
| `D3D12DDICAPS_TYPE` enumerators named in the corpus | **17 / 43** |

⭐ **So roughly a third of the DDI's function surface has prose somewhere, and the three hardest areas
in `DDI_REFERENCE.md` — resource binding (H3), resources/heaps, barriers — are among the best-covered.**

⭐ **And the corroboration cuts the other way, which is the reassuring half.** `OpenAdapter12`,
`pfnSetCommandListDDITableCb` and `pfnGetPresentPrivateDriverDataSize` appear **nowhere in the whole
corpus** (verified by grep) — exactly the three things `D12-G5` had to measure. The spy was not
redundant; it covered the part that genuinely has no documentation anywhere.

### 1.1 Baseline-table slot-name coverage, and the trap in counting it

Re-derived by parsing each table struct body out of `tmp/dx12/sdk/d3d12umddi.h` and word-matching each
member name across the corpus:

| table | named in prose |
|---|---|
| `D3D12DDI_DEVICE_FUNCS_CORE_0109` | **32 / 124** |
| `D3D12DDI_COMMAND_LIST_FUNCS_3D_0108` | **34 / 75** |
| `D3D12DDI_COMMAND_QUEUE_FUNCS_CORE_0001` | **1 / 7** (`pfnExecuteCommandLists` only) |
| `D3D12DDI_ADAPTERFUNCS_0109` | **4 / 8 nominal — but 2 / 8 real** |

⛔ **The adapter row is the trap, and it is worth stating because it is the exact error this session
was told to avoid.** Of the four nominal hits, `pfnFillDDITable` and `pfnGetSupportedVersions` occur in
the corpus **only** as members of the *Shader Compiler Plugin* DDI (`ShaderCompilerPlugin.md:502,504`)
— a **different DDI surface**, implemented by a different DLL, none of whose 27 `PFND3D12DDI_COMPILER_*`
typedefs exist in SDK 26100. Only `pfnGetCaps` (`ConservativeRasterization.md:899,902`,
`RasterOrderViews.md:267`) and `pfnDestroyDevice` (`BackgroundProcessing.md:291`) are the display DDI's.
**A name match is not a surface match.**

## 2. How to read the priority column

| | |
|---|---|
| **1** | Read in full. It settles an open Helios question or corrects a repo claim. |
| **2** | Read targeted. It plausibly closes a specific `UNVERIFIED` item. |
| **3** | A row and a pointer. No open question depends on it today. |
| **declined** | Out of scope at this milestone, **with the concrete reason**. |

⚠ **`PFN in SDK` is the column that matters most.** A spec with 27 `PFND3D12DDI_*` of which **0** exist
in SDK 26100 describes a DDI surface this driver cannot implement and must not advertise. Where the
ratio is low, check *which* symbols are missing before concluding the spec is useless — `ResourceHeaps`
scores 7/20 only because the misses are 2015-era draft suffixes whose shipping equivalents are all
present.

⚠ **A low symbol count does not mean low value.** `CPUEfficiency.md` scores 40 because it predates the
`PFND3D12DDI_*` naming convention and writes DDI names in prose; it is nonetheless one of the two
richest driver-contract documents in the corpus. `IndirectDrawing.md` scores **zero** and still carries
the only account of how `ExecuteIndirect` is lowered to the driver.

## 6. Traps in the corpus itself

Six ways this corpus will mislead a careful reader. Every one was hit at least once this session.

1. ⛔ **A spec's DDI code block is not the shipping shape.** These are drafting-era documents.
   `D3D12EnhancedBarriers.md`'s `D3D12DDI_RANGED_BARRIER_0094` has a 24-byte
   `D3D12DDI_BARRIER_SUBRESOURCE_RANGE_0088 Subresources` member where the shipping header has a 4-byte
   `UINT Subresource`. `ProgrammableSamplePositions.md`'s resolve prototype is **missing a parameter**
   — a thunk written from it has nine where the runtime passes ten, and every argument after
   `DstResource` shifts by one. **Take shapes from `d3d12umddi.h`, always.**
2. ⛔ **A name match is not a surface match.** `pfnFillDDITable` and `pfnGetSupportedVersions` appear in
   the corpus only as *Shader Compiler Plugin* members (§1.1).
3. ⛔ **Symbols that do not exist here.** 173 of the 296 `PFND3D12DDI_*` the corpus names are absent
   from SDK 26100. Whole features are gated above this build: RecreateAt at **0111**, GPU dumps at
   **0121**, revised view creation at **0121**, runtime bypass at **0114**, tiled resources tier 4 at
   **0117**. Helios negotiates **0110**.
4. ⛔ **Preview sections describe what nothing ships.** `D3D12EnhancedBarriers.md`'s entire *Fence
   Barriers* half is preview-only — *"The Fence Barriers preview requires developer mode."* — and every
   symbol it names is absent from the header. `ProgrammableSamplePositions.md`'s *Mixed Rate
   Rasterization* is developer-mode-only. `D3D12GpuDumps.md` is a v0.02 preview whose files carry a
   `.dxdmp_preview` extension.
5. ⛔ **Specs contradict each other, and the older one can be the stale one.** `SamplerFeedback.md:79`
   says *"Sampler feedback support is not required as part of a Direct3D feature level"*;
   `D3D12_FeatureLevel12_2.md:48` lists sampler feedback Tier 0.9 as an FL 12_2 requirement. The
   feature-level spec wins, and vkd3d-proton agrees with it.
6. ⛔ **Preserve typos verbatim.** `D3D12TiledResourceTier4.md:43` contains *"lastest"* and
   `ShaderCompilerPlugin.md:557` contains a doubled *"with with"*. Silently correcting either breaks the
   mechanical substring check that makes this register trustworthy. **The same applies to the header:**
   the adapter table's typedef is `PFND3D12DDI_FILLDDIT**T**ABLE` — doubled T — so a grep for the
   correctly-spelled `PFND3D12DDI_FILLDDITABLE` returns **zero hits** against three for the real name.
